# 空压站智能调度项目四人并行任务实施方案

## 1. 实施目标

四人采用“统一接口、分模块并行、阶段性集成”的方式，共同完成空压站多机协同智能调度 Agent。

总体原则：

- 先统一数据格式和接口，再并行开发；
- 各成员负责独立模块，避免同时修改同一部分；
- 算法未完成前使用模拟数据和 Mock API，其他成员无需等待；
- 每隔 1～2 天进行一次小规模集成；
- 每个阶段均形成能够运行和验收的版本。

## 2. 四人职责分工

### 成员 A：数据、负荷预测与健康诊断

负责：

- 数据体检、清洗、字段和单位统一；
- 生成标准化时序数据；
- 预测未来 15、30、60 分钟用气负荷；
- 根据振动、温度、电流等参数计算设备健康指数；
- 输出异常因素、风险等级和维护建议；
- 向成员 C 提供负荷预测和健康诊断调用函数。

验收指标：

- 数据处理流程能够重复执行；
- 负荷预测 MAPE 目标不高于 8%；
- 单次预测时间不高于 10 秒；
- 能输出 0～100 的健康指数；
- 能识别预设的振动、温度和电流异常；
- 结果包含异常原因和处理建议；
- 真实验证与仿真验证标识清楚。

### 成员 B：人工基线、调度优化与喘振安全

负责：

- 建立传统人工调度基线；
- 建立机组流量、功率、加载率和效率模型；
- 计算最优开机组合、负荷分配和压力设定值；
- 加入供气、备用容量、加载率、启停和健康约束；
- 计算喘振安全裕度和低、中、高风险等级；
- 对比人工调度与智能调度的能耗和稳定性；
- 向成员 C 提供调度优化和喘振评估调用函数。

验收指标：

- 调度结果满足预测用气需求和备用容量要求；
- 所有机组加载率处于允许范围；
- 单次调度生成时间不高于 30 秒；
- 完整调度决策周期不高于 60 秒；
- 模拟综合能效提升目标不低于 6%；
- 加载率偏离度目标不超过 ±10%；
- “大马拉小车”工况时长下降目标不低于 60%；
- 高喘振风险方案不能通过安全校验；
- 算法失败时能够输出安全回退方案。

### 成员 C：公共接口、后端、MCP、Agent与部署

负责：

- 建立项目目录、公共数据格式和 Mock 数据；
- 建立后端 API 和数据库；
- 接入成员 A 和成员 B 的算法模块；
- 建立负荷预测、调度优化、健康诊断、喘振预警和控制指令 5 个 MCP 服务；
- 实现自然语言 Agent 和工具调用流程；
- 实现模拟 SCADA、PLC、工单及控制反馈；
- 实现安全校验、人工确认、执行日志和失败回退；
- 完成 Docker 和 COSMO Code 平台部署。

验收指标：

- Mock 模式下后端可以独立运行；
- 5 个 MCP 服务均能被调用；
- Agent 能正确调用预测、诊断、调度和安全工具；
- 能完成至少 10 轮连续对话；
- 能处理“3号机振动偏高，请重新调度”场景；
- 未经人工确认的控制指令不得执行；
- 安全校验失败的方案不得下发；
- 重复确认不会造成重复执行；
- Docker 环境可以一键启动并通过健康检查。

### 成员 D：前端、系统测试与比赛材料

负责：

- 建立运行总览和机组状态页面；
- 建立负荷预测、调度方案、健康趋势和喘振风险页面；
- 建立能效分析、告警事件、Agent 对话和控制日志页面；
- 展示人工调度与智能调度对比；
- 制作负荷下降节能调度和设备异常安全重调度两个场景；
- 完成端到端测试和演示流程测试；
- 整理方案书、技术报告、PPT、视频脚本和答辩材料。

验收指标：

- 所有核心页面可以正常打开和刷新；
- 图表字段、单位、时间和设备编号正确；
- 实时、历史、预测和仿真数据标识清楚；
- 安全校验失败时页面不能执行控制操作；
- 两个典型场景可以启动、重置和重复演示；
- 接口失败、空数据和加载状态有明确提示；
- 端到端核心流程测试通过；
- 5～10 分钟演示流程能够稳定完成；
- 方案书、PPT和测试报告使用统一指标口径。

## 3. 并行实施流程

### 阶段一：公共基础准备

建议用时：半天至一天。

由成员 C 主导，四人共同确认：

- 项目目录；
- 设备编号和设备类型；
- 时间、压力、流量、功率等字段与单位；
- 预测、健康、调度和喘振结果格式；
- Mock 数据和 Mock API；
- 两个演示场景；
- 分支和代码合并规则。

阶段验收：

- A、B、D均能使用公共格式独立开发；
- D能够通过 Mock API 显示样例页面；
- 公共字段不存在含义或单位争议。

### 阶段二：四条工作线并行开发

四人同时开展：

| 成员 | 并行任务 | 初始依赖 |
|---|---|---|
| A | 数据清洗、负荷预测、健康诊断 | 真实数据与公共格式 |
| B | 人工基线、调度优化、喘振预警 | 公共样例数据 |
| C | 后端、数据库、Mock API、MCP框架 | 公共格式 |
| D | 页面、图表、交互和演示场景 | Mock API |

阶段验收：

- A能够输出标准预测和健康结果；
- B能够输出人工基线和优化调度结果；
- C能够在Mock模式启动全部主要接口；
- D能够在Mock模式展示全部核心页面。

### 阶段三：真实模块接入

接入顺序：

1. A向C交付预测和健康诊断函数；
2. B向C交付调度和喘振评估函数；
3. C将Mock Provider替换为真实Provider；
4. D将前端从Mock模式切换到真实API；
5. 四人共同检查字段、单位和异常处理。

阶段验收：

- 真实数据能够完成预测、诊断、调度和显示；
- 模块之间不需要人工复制文件或结果；
- Mock模式仍然保留，可用于离线演示；
- 所有接口错误均有明确提示和日志。

### 阶段四：典型场景联调

#### 场景一：负荷下降后的节能调度

1. 系统预测未来负荷下降；
2. 调度模块发现低效率运行；
3. 系统生成减少开机数量或调整加载率的方案；
4. 安全模块检查压力、供气和喘振风险；
5. Agent解释节能原因；
6. 用户确认后模拟执行；
7. 页面展示优化前后能耗对比。

#### 场景二：设备异常后的安全重调度

1. 3号机振动升高；
2. 健康模块输出预警；
3. Agent调用调度模块重新分配负荷；
4. 喘振模块检查替代方案；
5. 用户确认后模拟执行；
6. 系统记录决策、控制结果和维护建议。

阶段验收：

- 两个场景可以从头到尾完整运行；
- 所有决策均有原因；
- 危险方案能够被系统阻止；
- 用户拒绝方案时不会执行控制指令；
- 场景可以重置和重复演示。

### 阶段五：指标验证与比赛交付

四人共同完成：

- 使用统一测试集计算最终指标；
- 检查所有指标的计算口径；
- 完成性能、接口和端到端测试；
- 完成Docker与COSMO Code部署验证；
- 完成方案书、技术报告、PPT和视频；
- 完成现场演示排练和答辩准备。

阶段验收：

- 完整调度周期不高于60秒；
- 关键算法指标均能通过脚本重复计算；
- 真实、回测和仿真指标明确区分；
- Docker和COSMO Code环境均可运行；
- 演示流程连续运行至少三次无阻断；
- 文档、页面和答辩使用相同数据与指标。

## 4. 模块依赖关系

```text
公共接口与Mock数据
├─ A：预测与健康 ─────┐
├─ B：调度与安全 ─────┼→ C接入真实模块 → D端到端测试
├─ C：后端与Agent ────┤
└─ D：Mock前端与演示 ─┘
```

约 80% 的开发工作可以并行；公共接口确认、真实模块接入和最终联调需要按依赖顺序完成。

## 5. 集成与沟通机制

- 每天进行一次 15 分钟进度同步；
- 每隔 1～2 天将可运行功能合并到集成分支；
- 每次合并后执行统一自动测试；
- 公共接口只由成员 C 统一维护；
- 接口变化必须说明影响范围，并尽量保持向后兼容；
- 每位成员每天说明完成内容、测试结果、依赖和阻塞项；
- 不允许等所有模块开发结束后再进行第一次联调。

## 6. 最终共同验收

项目最终必须完整跑通：

```text
读取空压站状态
→ 预测未来用气负荷
→ 诊断设备健康
→ 生成多机调度方案
→ 校验喘振和供气安全
→ Agent解释决策
→ 用户人工确认
→ 模拟下发控制指令
→ 返回执行反馈
→ 保存决策与执行日志
```

共同验收标准：

- 四个成员负责的模块能够在同一系统中运行；
- 核心调度决策周期不高于 60 秒；
- 调度结果满足供气与安全约束；
- 调度结果具有明确、可读的解释；
- 控制操作经过安全校验和人工确认；
- 两个典型场景能够稳定、重复演示；
- 所有指标都有可追溯的计算依据；
- 最终应用、文档、PPT和视频内容保持一致。
